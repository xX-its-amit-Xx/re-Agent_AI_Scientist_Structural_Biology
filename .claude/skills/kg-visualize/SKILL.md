# Knowledge-graph visualization

A graph nobody looks at is a database. The point of this skill is that a reader
can see, in one picture, what the target resembles and how strongly — and can
interrogate any single claim without leaving the page.

## Guard rails

- **Self-contained output, always.** The publish target blocks every external host:
  no CDN, no remote fonts, no runtime `fetch`. Third-party JavaScript is vendored
  under `assets/vendor/` and inlined at render time. Run `reagent assets fetch` if
  it is missing. A page that silently fails to load its library renders as a blank
  box, and you will not notice until someone else does.
- **Nine predicate families, at most seven visible.** Colour encodes the *family*,
  never the individual predicate — there are ~30 predicates and the ceiling for a
  colour-blind-safe categorical palette is about eight. Dash pattern separates
  predicates inside a family; the exact predicate is on hover. Evidence and data
  families are hidden by default because every claim has sources and every entity
  has data pointers, so they would bury everything else.
- **Normalise edge width inside its own axis.** A TM-score of 0.8 and a Tanimoto of
  0.8 are different claims. `AxisSpec.score_range` exists for this; drawing them at
  equal thickness is the most likely way this system lies to a reader.
- **Never draw the whole graph by default.** Use the focal node's k-hop
  neighbourhood with a per-node fan-out cap. A hairball is not a figure.
- **State the truncation on the page.** The renderer records which nodes had their
  fan-out capped and how many edges fell outside the depth horizon, and prints it
  in the subtitle. A figure that hides its own truncation reads as "this is
  everything", which is a lie.
- **Every figure declares its question.** The `Visualization` contract rejects a
  figure whose `question` is not phrased as one. If you cannot write the question,
  delete the figure.

## The graph view

```bash
reagent viz kg --focal uniprot:O75469 --problem reports/<run>/problem.json \
  --depth 2 --fanout 30 --out docs/figures/kg.html
```

Passing `--problem` matters: the axes come from the `ProblemSpec`, so edge width is
normalised per axis rather than guessed. Without it every scored edge is drawn thin.

The renderer returns the `Visualization` contract object alongside the file, so the
report's declared encoding is generated by the same code that paints the pixels
and the two cannot drift apart. Put it straight into the report's `VizBundle`.

### What the reader gets

Rings are graph distance from the focal node; node colour and shape encode entity
type (shape is a redundant channel, so the figure survives greyscale printing);
edge colour is the predicate family; dash separates predicates within a family;
thickness is the score normalised within its axis; opacity is confidence. Hovering
an edge shows its predicate, every quantitative attribute, its confidence, and its
citations. Clicking an edge isolates that predicate across the whole graph;
clicking a node isolates its neighbourhood. There is a search box and a
family-filter checklist, and a force layout as an alternate view.

### Multiple metrics on one edge

An edge should accumulate all the evidence for that relationship, not one number.
The store *merges* `attrs` when the same triple is asserted twice, so several
skills can each contribute a metric:

```
uniprot:O75469 --SIMILAR_FOLD_TO--> uniprot:Q14994
  attrs: {tm_score: 0.87, rmsd: 1.9, aligned_len: 241,
          sae_feature_overlap: 0.81, shared_pocket_residues: 19}
```

Thickness comes from the axis's declared `score_key`; the rest appear on hover and
are queryable in SQL. Adding metrics therefore costs nothing visually. **When
metrics disagree — high fold similarity, low pocket similarity — that disagreement
is a finding**, and worth its own annotation.

## Why Cytoscape.js, and why not Obsidian

**Cytoscape.js** is inlined (435 KB, MIT, zero dependencies). It was chosen because
three things we need are all built in: automatic fanning of *parallel edges* (two
proteins related on four axes must show four distinguishable edges, and this is the
only mainstream library where that is zero-effort), a genuine concentric/ego
layout, and a selector engine that makes "isolate one predicate" a one-liner. It is
also the lingua franca of computational biology, so a reviewer will recognise it.

**Obsidian was evaluated and rejected as the primary view.** It is a reasonable
*secondary* browsing layer and the exporter is cheap, but it cannot do the job:

- **Edge weight is unrepresentable.** Obsidian's link model is (source, target,
  optional display alias) — there is nowhere to put a per-edge number that any
  renderer reads. `[[X|tm_score=0.82]]` sets a display alias, not a weight. Typed
  edges *can* be coloured (only via the Extended Graph plugin, reading frontmatter
  or Dataview inline fields), but thickness can only be driven by *computed* graph
  statistics, never by our stored scores. Our stated requirement is that type and
  weight are both encoded, so this alone disqualifies it.
- **Scale.** The one load-bearing plugin is documented and tested to roughly
  400-600 nodes. A real Stage 1 graph is 500-5,000.
- **Parallel edges collapse.** Obsidian draws one line between two notes.
- **No programmatic layout, no legend, no reproducible figure.** You cannot script
  "pin the target at centre and lay rings by score".
- **Single-plugin dependency risk.** Typed edges rest entirely on one
  solo-maintained plugin, in the ecosystem's highest-churn category — the previous
  three plugins in this niche are all abandoned.
- **Obsidian Publish runs no community plugins**, so a shared vault shows
  teammates the unstyled monochrome graph regardless.

So: `reagent viz kg` for the real figure. The Obsidian export exists because once
the JSONL is written it is nearly free, and wiki-style browsing with backlinks and
hover previews is genuinely pleasant for *reading* the graph. Use it for
exploration, never as the deliverable.

### Exports for other tools

- **GraphML** — for Gephi (publication-quality static layouts) or Cytoscape desktop
  (the bio-focused one, scriptable via py4cytoscape). Use when you want a
  print-quality figure or real network analysis.
- **Obsidian vault** — one Markdown file per node, edges as frontmatter typed links
  plus Dataview inline fields carrying the payload. See
  [obsidian-export.md](reference/obsidian-export.md) for the exact convention,
  including why every edge is emitted twice.

## The other required figures

A graph view alone does not discharge a stage's visual obligation. `EXPECTED_VIZ`
in the contract names what each stage should show, and `reagent report validate
--strict` fails a stage that is missing them. The three that recur:

**Axis-agreement heatmap.** Neighbours on the vertical axis, similarity axes on the
horizontal, cell = normalised score. This is the figure that shows whether the axes
agree, and disagreement is informative: an entity that is a fold neighbour but not
a pocket neighbour is a different kind of template than one that is both.

**Domain-shift distribution.** Nearest-neighbour similarity from each test item to
the known set, as a histogram with the subpopulation split marked. Never plot the
mean — bimodality is the whole point, and a mean hides it.

**Data availability matrix.** Entities or pairs against measurement kind, shaded by
how many datasets exist and whether they are open. The *holes* in this figure are
the finding.

## Anti-patterns

- **The hairball.** Everything, force-laid, one colour. Contains all the
  information and conveys none. The contract's `n_elements` guard rejects a figure
  above 5,000 elements with no declared clustering, aggregation, or filtering.
- **Colour carrying two meanings.** Node colour for type and edge colour for
  family is fine, because they are different marks. Edge colour for both family and
  confidence is not.
- **A legend the reader must cross-reference to make sense of anything.** If
  understanding the picture requires memorising nine colours, add interaction
  (hover, click-to-isolate) so colour only has to narrow the field, not identify.
- **Unnormalised weights across axes.** Covered above, and worth repeating: it is
  the failure that misinforms rather than merely confuses.
- **A figure with no takeaway.** The `takeaway` field must say what the figure
  shows, not restate what it asks. If the honest takeaway is "the graph is sparse
  here", write that — a negative result stated plainly is worth more than a
  flattering picture.
